# Review use

Review how Courtyard was really used in a window, so features nobody uses, or that models misuse, don't pile up: removal is the default (`docs/agents/process.md`, Reviewing use). This works on Courtyard's own repository only: if `packages/skills/review-use/scripts/review-use.ts` isn't in the worktree, say this skill reviews Courtyard and must run in its code workspace, and stop.

1. **The window** is the last 14 days, to today, unless the owner names another. Say it in your first line.
2. **What merged.** List the pull requests merged in the window: `gh pr list --state merged --search "merged:<since>..<until>" --json number,title,body,mergedAt --limit 200`. The user-facing features are the ones whose body has a `What's new:` line; each is one feature, named by that line.
3. **What was used.** Run the script, from the worktree, naming the data folder, which is the worktree's folder two up (`<data>/worktrees/<session>`): `node packages/skills/review-use/scripts/review-use.ts --data ../.. --since <since> --until <until>`, adding `--context <folder>` when the owner has given the context folder's path, so workspaces show by name. It reads outside the worktree, so the owner is asked to allow it: say first, in a line, that it reads only the session logs and workspace names and sends nothing anywhere. It reads only `sessions/` in the data folder and each `workspace.json` in the context folder, and gives four sections: Workspaces, What the owner said, Signals and Builders. Never read the data folder any other way.
4. **Judge each feature** from those sections: **used** (its signals show and the owner's words use it), **misused** (models used it wrongly: saves undone or edited, approvals denied, the owner correcting a model, a skill loaded where it didn't fit) or **unused** (no sign of it). Give each its counts and at most two short quotes of the owner's that show it. A feature merged under a week before the window's end is **in trial**: say so, and keep it unless it's misused.
5. **Write the review**, short: a table of the features (Feature, PR, Use, Evidence, Suggest), then the builders' numbers (model work against waiting, approvals, stalls: carried on, idle with no PR, at the limit), then each model mistake found, in a line. Suggest **keep**, **fix** or **remove** for each feature: unused after its trial is remove, unless the owner says otherwise; misused is fix, or remove when models keep misusing it. End by asking the owner to tick, or change, each suggestion.
6. **File what the owner ticks**, once they have: each fix and each remove as its own issue with `gh issue create`, in a milestone (`Later` when unsure), with a category label (`enhancement`, or `bug` for a misuse) and `needs-triage`, saying what was found and what to do. Keep: nothing filed. Then file one issue, "Context eval: the model mistakes the <since> to <until> review found", listing each mistake, so each is added to `apps/worker/eval/scenarios.ts` as a scenario.
7. **Nothing personal leaves the session.** The repository and its issues are public: an issue or a scenario says what a feature did wrong in general words, with invented examples, never the owner's quotes, their workspaces' names or what's in them. The quotes stay in your answer.
